# Jupiter の RDP を Tailscale 経由だけに限定する

## 背景と課題

Jupiter の KRdp は `0.0.0.0:3389` で待ち受ける。従来は RFC1918 の
プライベートアドレス全域と Tailscale の CGNAT 範囲からの接続を許可していた。
プライベートアドレスはネットワークの所有者を識別しないため、Jupiter を外部の
アクセスポイントへ接続した場合も RDP へ到達される可能性がある。

RDP は shishi のシステムパスワードで PAM 認証する。認証後は NOPASSWD の
`sudo` を利用できるため、到達範囲を認証済みネットワークに限定する必要がある。

## 判断基準

* Tailscale を経由しない物理 LAN と外部のアクセスポイントから
  3389 番ポートへ到達できないこと
* 既存の Tailscale ノード認証と通信ポリシーを利用すること
* RDP クライアントから Jupiter へ直接接続できること
* 独自のファイアウォールスクリプトを保守しないこと

## 検討した選択肢

1. `tailscale0` だけで 3389 番ポートを許可する
2. 自宅 LAN のサブネットだけを送信元として許可する
3. 3389 番ポートを閉じ、SSH トンネルだけを使う

## 決定

**採用:** `tailscale0` だけで 3389 番ポートを許可する。
RDP クライアントは Jupiter の MagicDNS 名または Tailscale IP へ接続する。
tailnet 内で 3389 番ポートへ到達できる主体は Tailscale の通信ポリシーに従う。

Tailscale SSH は 22 番ポートの SSH 接続を扱う。RDP は Tailscale が提供する
ネットワーク上で 3389 番ポートへ直接接続するため、Tailscale SSH を経由しない。

### 影響

**良い影響:**

* 接続先の LAN が使うプライベートアドレス範囲に関係なく RDP を遮断できる
* Tailscale のノード認証と WireGuard の暗号化を RDP の前段で利用できる
* NixOS のインタフェース別ファイアウォール宣言だけで構成できる

**悪い影響:**

* Tailscale が停止している間は RDP を利用できない
* 物理 LAN のアドレスへ RDP クライアントから直接接続できない
* RDP の PAM 認証と NOPASSWD の `sudo` という侵害時の経路は残る

**中立的な影響:**

* tailnet の通信ポリシーは Tailscale 管理画面で管理する
* SSH と RDP は別のポートと認証経路を使う

### 確認方法

Nix の契約検査で、3389 番ポートを許可するインタフェースが `tailscale0` だけで
あることを確認する。全インタフェースの許可と独自のファイアウォールコマンドに
3389 番ポートが含まれないことも確認する。実際の RDP 接続と tailnet の通信ポリシーは
実機で確認する。

## 各選択肢の比較

### `tailscale0` だけで許可する

* 利点: 接続元と接続先を Tailscale のノードとして認証できる
* 利点: 外部のアクセスポイントが同じアドレス範囲を使っても到達できない
* 利点: RDP クライアントから直接接続できる
* 欠点: Tailscale の可用性に依存する

### 自宅 LAN のサブネットだけを許可する

* 利点: Tailscale が停止していても自宅 LAN から接続できる
* 欠点: 外部ネットワークが同じサブネットを使う場合は到達できる
* 欠点: IP アドレスだけでは自宅 LAN を識別できない

### SSH トンネルだけを使う

* 利点: 3389 番ポートをネットワークへ公開しない
* 利点: SSH の認証後だけ RDP へ到達できる
* 欠点: RDP 接続のたびにトンネルを準備する必要がある
